# Baseline: QNN built-in MatMul on SM8650 v75 (frozen 2026-04-22)

Source: `example/qnn_matmul_profile/sweep_data_2026-04-19/sweep_summary.json`
(re-used; device + QNN SDK unchanged). Metric: QHAS `timeline_cycles` for the
MatMul compute kernel, extracted by `parse_qhas.py` with its UNK→HMX fix.

All four configs use the `q::ConvLayer_s1.opt` kernel (HMX-resident) except
fp16 which uses `q::ConvLayer.fp16.s1.tcm`.

## compute cycles × shape

| shape | fp16   | w8a16   | w8a8    | w16a16†  |
|-------|-------:|--------:|--------:|---------:|
| 32³   |  1,672 |   3,494 |   2,554 |    1,931 |
| 128³  |  3,363 |   4,758 |   3,352 |   11,552 |
| 256³  |  9,544 |   8,651 |   3,519 |   84,031‡|
| 512³  | 52,231 |  29,501 |  12,237 |  564,055‡|

cycles per MAC at 512³:
- w8a8    →  9.1e-5
- w8a16   →  2.2e-4
- fp16    →  3.9e-4
- w16a16  →  4.2e-3   (48 HMX tile calls; `Agent/qnn_matmul_dtype_comparison.md`)

†w16a16 is `q::ConvLayer_s1.opt` but with a flat [1,1,M,N] layout → 48 HMX
tile calls at 512³ instead of 2 for fp16. Slow despite 85.6% HMX utilization.
‡At 256/512³, profiler lumps its cycles into `SystemService(lumped)` —
workaround by re-parsing chrometrace for per-tile count. Use these numbers
as upper bound until re-run.

## Targets (from approved plan)

- **w4a16** ≤ 2× w8a16 cyc/MAC → ≤ 4.4e-4 cyc/MAC (≤ 59,002 cycles at 512³)
- **w4a8** ≤ 2× w8a8 cyc/MAC → ≤ 1.8e-4 cyc/MAC (≤ 24,474 cycles at 512³)
- **w16a16 beat track** ≤ 300µs (vs QNN's 581µs at 512³)
- **w16a16 match track** = same 48 HMX tiles, per-tile cycles within 10%
- All: sim↔device cyc/MAC within 5%

## How to re-run

```sh
    --device oneplus --connect ssh --arch v75 --shape 512,512,512
python example/qnn_matmul_profile/parse_qhas.py example/qnn_matmul_profile/output
```

To include our custom op in the same sheet, see Phase 0 extension note
below (`profile_all.sh --custom-ops all`, pending implementation).

## Phase 0 deferral

We deferred extending `profile_all.sh` to include custom-op rows inline.
Rationale: the QNN built-in baseline is already captured and the
custom-op-side measurements come from each op's own `run_on_device.sh` in
a matching format (cycles + cyc/MAC). Unified CSV is nice-to-have but not
load-bearing for Phase 1 RE. Revisit after Phase 3/4 when we need side-by-
side comparison plots for the final write-up.
