# P1.1 — V73 unaligned kernel test (2026-04-29)

执行：build with `V9_PROBE_REGIONS + V9_PROBE_V73_UNALIGNED`，对比 V73DEEP probe。

## PMU 测量（probe baseline V0，同 descriptor，仅换 kernel symbol）

| Kernel | A (prologue) | B (per-outer) | C (per-loop1) | D (per-loop0) | V0 ANY |
|--------|-------------:|--------------:|--------------:|--------------:|-------:|
| V73DEEP `hmx_v73_convbbb1x1deep_stride1` | 396 | ~0 | 8.9 | 8.4 | **1724** |
| V73 unaligned `hmx_v73_convbbb1x1_stride1_unaligned` | 148 | 233 | 0.8 | -2.2 | **829** |

V73 unaligned 的 V0 总 packet 数 = **829** vs V73DEEP **1724** = **~2× 减少**！

注意：unaligned 的线性拟合 D 出现负值（V1 = 1048 反而 > V0 = 829），说明
unaligned kernel 在不同 r20/r28 下走不同代码路径（可能 r20=1 触发了一条
slow path）。所以 D/C/B 的解释不是单纯每-iter cost。但 **V0 baseline 数字
是真实 measured 的**。

## Disasm 关键发现

V73 unaligned 用 **`:single:cm`** modifier (loop body lines 85-86)：

```
2eb8b8: { activation.ub = mxmem(r6,r7):single:cm
         weight.b = mxmem(r8,r31):single }  :endloop0
```

vs V73DEEP 用 `:deep:cm`：

```
2ebf28: { ...; activation.ub = mxmem(r6,r7):deep:cm
         weight.b = mxmem(r8,r9):deep }
```

按 `docs/hmx-programming-guide/06-instr-activation-load.md`：
> ### `:single` (F) — conv 只做 1 个空间位置
> 对应 Conv2D 的 kernel-size=1 × stride=1 模式。matmul 用不到。
> `libQnnHtpV75Skel.so` 里有用（conv 1×1）。

**`:single` 就是 1×1 conv 的"正经"模式 —— 我们的 case (matmul-as-1×1-conv) 正是它的目标场景。**

`:deep` 是"深通道流水"模式，文档里写"matmul 不用"。所以 V73DEEP 实际上不是给
matmul 优化的，是给某种 conv 用的。

## 但 production 跑不起来

`V9_KERNEL_V73_UNALIGNED` build 直接跑（chain=1 或 chain=8）都 SIGSEGV。
Graph execution failure。

可能原因（按可能性排）：

1. **Unaligned kernel 期望 input pointers 是 byte-aligned (非 tile-aligned)**：
   kernel 入口有 `r12 = and(r12, r7); r12 = ct0(r12)` 之类的位计算，对 tile-aligned
   输入（low bits 全 0）会得到 32（"trailing zeros"），后续 `r12 -= 5 → 27` 然后
   `r13 = 1 << 27` 等等 —— 最终可能算出无效的 loop trip 让 kernel 越界访问
   activation buffer 外的内存。
2. **Unaligned 期望 ad/od 字段语义不同**：例如 n_act_pairs 在 unaligned 里是 K-bytes
   而不是 K-tiles。
3. **Unaligned 需要不同 mask 配置**：mask[+0x18] 用作不同 stride。

需要进一步 debug 才能让 unaligned 在 production 工作。

## 关键线索 native 怎么做到 346 packets

Native 使用 `q::ConvLayer_s1.opt@CB*2.Xsb.Fi.t.fi` 这个 template，这个
template 大概率 dispatch 到 **某个 `:single` mode kernel 调用**（因为
1×1 matmul 是 `:single` 的本职），而不是 `:deep`。

我们 dlsym 调用 `hmx_v73_convbbb1x1deep_stride1` 时走的是错误的 modifier
（`:deep` for matmul = 不对的 semantics）。

native 可能调的是 `hmx_v73_convbbb1x1_stride1` (非 deep)，但它 dispatcher
里检查 `tstbit(r28, #5)` 然后 jump 到 deep variant —— 如果 native 设的
mask 的 deep flag 是 0，它就**留在 `:single` 路径**。

这个 hypothesis 可以测：跑 V73 non-deep with `set_hmx_params_conv1x1(0x700, 0, 0, 0, 0)`
（arg5=0，**不**设 deep flag）。我们测过 V73 non-deep with `arg5=0x20`（设 deep flag）
是 1.74× 慢于 V73DEEP；没测过 arg5=0 的版本。

## 接下来推荐 — 但很可惜，假设被打脸

**假设**："V73 non-deep with arg5=0 走 `:single` body" — **错误**。
检查 `hmx_v73_convbbb1x1_stride1` (0x2eadc0) disasm 显示 non-deep body 也用
`:deep:cm`，arg5 控制的是 dispatch 到 deep variant 与否，不是 modifier。

`:single:cm` 只在 `*_unaligned` 变体里（0x2eb780, 0x2eb380）。Production
跑会 crash。

V73 unaligned probe 数据本身也有疑点：V1/V2 ANY > V0 ANY 是反常的（更小的工作
量却更多 packets），很可能 kernel 在 V1/V2 输入下进入无限循环或越界，PMU 快照
拿到的是 partial count。**V0 = 829 也可能不是真实完成的工作量**。

## 真实结论

`:single:cm` 是 1×1 matmul 的"正经" modifier，但 v75 的 `:single:cm` kernel
（`hmx_v73_convbbb1x1_stride1_unaligned`）需要 unaligned input pointer 配置
我们没法满足。所有 `aligned` 1×1 bbb kernel (V73 / V73DEEP / OLD) 都用
`:deep:cm` 或 `:cm`，packet 数都 > 700 量级。

**Native 346 packets 仍然神秘 — 不在 dlsym 路径能访问的范围内。**
