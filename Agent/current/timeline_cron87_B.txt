WHAT LEVER B DOES (gp_renorm_i16, gdn_pure_solve.cpp ~528 helper + solve_head ~972 site, #ifdef GP_INPLACE_RENORM)
  The 6 lower-tri off-diag merges end with `MM64 -> cv (T_ij) -> gp_acc_from_cv(acc, T_ij) ->
  gp_renorm(acc, T_ij)`. There gp_acc_from_cv SIGN-EXTENDS the fresh int16 cv into the int32 acc with
  NO accumulation, then gp_renorm immediately reads absmax + asr-sat back to int16. The int32 acc is a
  pure round-trip there (the cv already holds the only operand). gp_renorm_i16 computes the SAME shift s
  and the SAME saturating-asr DIRECTLY on the int16 cv block. The diag(4) and merge-S Σ_k acc are
  UNTOUCHED — those genuinely overflow int16 and need real int32. Production byte path unchanged (#else).

  BIT-EXACTNESS (the head risk — device-verified, see below). Equivalent to the int32 path PROVIDED the
  cv stays in [-32639,32639] (no -32768): then int16 absmax == int32 absmax; for v fitting int16,
  sxt32(v) asr s == int16 v asr s; and for the s<0 left-shift, the renorm shift-select guarantees
  max|val|<<(-s) <= 16384 < 32639 so Q6_Vh_vasl_VhR cannot drop high bits (clamp ±32639 then matches).
