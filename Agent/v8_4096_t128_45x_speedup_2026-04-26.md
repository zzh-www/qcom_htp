# V8 4096³ M_TILE=128 = 4.6× speedup（2026-04-26）

## 现状（gen_v8_graph.py 自适应 tile 之后）

| Shape | V8 iter2 | Native iter2 | V8/native |
|-------|---------:|-------------:|----------:|
| 256³  | 40us     | 28us         | 1.43×     |
| 512³  | 88us     | 64us         | 1.38×     |
| 1024³ | 361us    | 585us        | **0.62×** ✓ |
| 2048³ | 2375us   | 2786us       | **0.85×** ✓ |
| 4096³ | 17491us  | 13240us      | **1.32×** (was 6.04×) |

**U 形分布**：1024-2048 段 V8 已经比 native 快；只剩 256/512 (轻 1.4×) 和 4096 (1.32×) 有 gap。

## 触发改动

`example/hmx_matmul_phase3/standard_flow/phaseB_v8/gen_v8_graph.py`
`plan_matmul_graph()` 在 max(M,K,N) ≥ 4096 时自动 `M_TILE=N_TILE=128`，否则保持 256。

## 触发的根因（从 spill/fill ratio 推出）

| Shape | tile | spill MB | fill MB | fill/spill | wall |
|-------|------|---------:|--------:|-----------:|-----:|
| 4096³ | 256 | 60 | 431 | **7×**  | 80ms |
| 4096³ | **128** | 27 | 484 | 18× | **17.5ms** |
| 4096³ | 64  | 27 | 776 | 30× | 22ms |

t=128 是甜点。t=256 让 VTCM-resident tile 太大，整个 K-loop 期间存活的数据被频繁淘汰；t=64 让节点数爆炸 (4417 nodes vs 1185 at t128) 调度开销盖过了。

Native 4096³ 对比：spill 158 MB / fill 158 MB，**1:1 重用率**。我们 t128 是 18:1。这是剩余 1.32× gap 的主因，未来要靠显式 ActToVtcmCache + InputSlicePad 拓扑才能压平。

## memory 修正

老 memory 条目 "V8 apples-to-apples 真实 wall 比例：512³=10.5×, 1024³=17.7×, 2048³=21.6×" **完全错**（可能是早期 cycle 口径混淆 + 过期数据）。今天实测：V8 在 1024-2048 已经比 native 快 0.62-0.85×。


## 下一步候选（按预期收益排）

1. **4096³ ActToVtcmCache** — 显式把整块 act 一次进 VTCM (~16 MB > VTCM 8MB 不行；需要 K-banded staging)。理论上能从 18× fill/spill 降到 ~3-4×，估计 17.5ms → 14ms 接近 native。
2. **256³/512³ 小 shape op fusion** — 把 Slice + PackActivation 合一个 op，消除 ONNX::Slice 中间节点开销。预计能压 5-10%。
3. **Phase 2 dlsym ConvLayerS1Opt** — 把 MatMulV8 内核换成 hmx_convbbb1x1_stride1。已有脚手架（V8_USE_DLSYM_PER_TILE）。但单 instance cycle 已贴脸 ceiling，估计收益<5%。
